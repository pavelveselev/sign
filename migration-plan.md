# План реализации: сервис оркестрации подписания документов

Документ для Claude Code. Прочитай его целиком до начала работы. Работай по этапам из раздела 9 и останавливайся после каждого этапа для ревью.

## 1. Контекст и цель

Нужен сервис, который ведёт документы организации по маршрутам подписания. Сам сервис ничего не подписывает: подписывает сторонний софт, а сервис инициирует запросы на подпись, отслеживает их результат и двигает документ по этапам.

Состав системы:

- **БД Oracle.** Одна база и для таблиц сервиса, и для интеграции со сторонним софтом.
- **Сервис** (этот репозиторий). .NET Worker, развёртывается в Kubernetes, несколько реплик.
- **Софт подписания.** Подписывает автоматически или руками сотрудников, сам уведомляет подписантов, кладёт подписанные файлы в папку, выставляет статусы в БД.
- **SMB-шара.** Оттуда сервис в некоторых случаях читает подписанные файлы.

Объём: десятки документов в день. Производительность не является целью, цель — надёжность и простота сопровождения.

Исходное состояние репозитория: VS solution с одним проектом, только что созданным из шаблона `worker`.

## 2. Принятые решения

Эти решения приняты, не пересматривай их без явного запроса.

| Решение | Обоснование |
|---|---|
| Свой движок маршрутов, без BPMN-движков, Temporal, MassTransit | Маршруты простые, меняются разработчиками, объёмы малые |
| Без брокера сообщений, только polling БД | Источник правды — БД, брокер не убирает опрос и добавляет двойную запись |
| Сервис — инициатор всех взаимодействий | Входящих HTTP-вызовов и callback'ов нет |
| Маршруты описываются в коде классами: один класс на тип документа, версии и этапы внутри него. Fluent API нет | Визуальный редактор и изменение маршрутов «на лету» не нужны; маршрут типа документа целиком виден в одном файле |
| Очередь работ — таблица сервиса, захват через аренду (`locked_by`, `locked_until`) | Аренда истекает сама, если реплика упала |
| Захват оптимистичным `UPDATE`, без `FOR UPDATE SKIP LOCKED` | В Oracle `SKIP LOCKED` плохо сочетается с ограничением числа строк |
| Статус маршрута, текущий этап, состояние этапа и аренда — четыре независимых понятия | Этапы свои у каждого типа документа, статусы общие |
| Этапы только последовательные | Параллельное подписание одного файла зависит от формата подписи, в первой версии не нужно |
| Время берётся из БД (`SYSTIMESTAMP`), не из часов реплики | Реплики не должны расходиться в оценке дедлайнов и аренды |
| Доступ к данным: ODP.NET (`Oracle.ManagedDataAccess.Core`) и явный SQL, допустим Dapper. Без EF Core | SQL захвата и переходов должен быть виден и контролируем |
| DDL — нумерованные SQL-скрипты в репозитории, сервис схему при старте не меняет | Схему накатывает Oracle-разработчик |
| Подписанный файл копируется в BLOB в схеме сервиса | Шара — транспорт, а не хранилище; требование хранить в БД несколько лет |

## 3. Допущения и открытые вопросы

Требования ещё уточняются. Ниже рабочие допущения. Каждое изолировано за абстракцией, чтобы его смена не задевала движок. Не блокируй работу на этих вопросах, но и не расширяй допущения молча: если реализация требует решения, которого здесь нет, остановись и спроси.

| № | Вопрос | Рабочее допущение | Где изолировано |
|---|---|---|---|
| 1 | Версия Oracle | 19c или новее (identity-колонки, `IS JSON`) | DDL-скрипты |
| 2 | Откуда приходят новые документы | Вьюха входящих документов во внешней схеме (раздел 6) | `IIncomingDocumentSource` |
| 3 | Атрибуты документа для условий маршрута | JSON-строка во вьюхе входящих | `DocumentContext` |
| 4 | Хэш исходного документа на старте | Отдаёт вьюха входящих, колонка может быть пустой | `DocumentContext` |
| 5 | Автоматическое и ручное подписание | Для сервиса выглядят одинаково: создать запрос, опрашивать статус. Отличаются параметром | `IStageHandler` |
| 6 | Есть ли у софта статус отказа | Есть. Если окажется, что нет, отказ вырождается в таймаут | `ISigningGateway` |
| 7 | Когда читать файл с шары | Если в результате запроса заполнен `file_ref` | `ISignedFileSource` |
| 8 | Способ доступа к SMB из Kubernetes | Не выбран (CSI-монтирование или SMB-клиент в приложении) | `ISignedFileSource` |
| 9 | Реальные типы документов и маршруты | Неизвестны. Делаются два маршрута-примера | Папка с маршрутами |
| 10 | Реакция на таймаут этапа | Маршрут завершается статусом `EXPIRED`, эскалаций нет | Политика этапа |
| 11 | Срок хранения и очистка | Не определены, очистка вне объёма | — |

## 4. Целевая структура solution

Сначала определи фактические имена solution и проекта и целевой фреймворк. Ниже `<Root>` означает корневое пространство имён существующего проекта. Целевой фреймворк существующего проекта не меняй.

```
<Root>.Core            движок, модель, классы маршрутов, абстракции. Не ссылается на Oracle и файловую систему
<Root>.Infrastructure  реализации абстракций: Oracle, файлы
<Root>                 существующий Worker: хост, DI, конфигурация, цикл опроса
<Root>.Tests           модульные тесты Core на фейках
<Root>.IntegrationTests  тесты Infrastructure на реальном Oracle в контейнере
db/service/            DDL схемы сервиса, нумерованные скрипты
db/contract/           спецификация внешнего контракта: вьюхи и процедуры
db/stub/               заглушка внешней стороны для разработки и тестов
```

Граница между `Core` и `Infrastructure` обязательна: вся логика переходов живёт в `Core` и тестируется без БД.

## 5. Модель данных сервиса

Префикс таблиц `SGN_`. Временные колонки — `TIMESTAMP WITH TIME ZONE`. Первичные ключи — identity.

**`SGN_ROUTE_INSTANCE`** — экземпляр маршрута, одна строка на документ.

| Колонка | Назначение |
|---|---|
| `id` | PK |
| `external_doc_id` | Идентификатор документа во внешней системе, уникальный |
| `doc_type` | Тип документа |
| `attributes` | JSON атрибутов документа |
| `content_hash` | Хэш исходного документа, может быть пустым |
| `route_code`, `route_version` | Маршрут, зафиксированный при старте |
| `status` | `ACTIVE`, `COMPLETED`, `REJECTED`, `EXPIRED`, `CANCELLED`, `FAILED` |
| `status_reason` | Код причины для конечных статусов |
| `current_stage_id` | Ссылка на текущий этап, пусто до первого шага |
| `attempts` | Число подряд идущих технических сбоев |
| `next_attempt_at` | Когда запись можно брать в работу |
| `locked_by`, `locked_until` | Аренда |
| `created_at`, `updated_at` | |

**`SGN_STAGE_INSTANCE`** — этап маршрута, строка создаётся при входе в этап. Хранит историю.

| Колонка | Назначение |
|---|---|
| `id` | PK |
| `route_instance_id` | FK |
| `stage_key` | Ключ этапа из описания маршрута |
| `state` | `PENDING`, `REQUESTED`, `DONE`, `REJECTED`, `EXPIRED`, `FAILED` |
| `request_id` | Идентификатор запроса на подпись, генерирует сервис, уникальный |
| `requested_at`, `deadline_at`, `finished_at` | |
| `reason` | Причина отказа или ошибки |

**`SGN_SIGNED_ARTIFACT`** — подписанный файл: `id`, `stage_instance_id`, `content` (BLOB), `sha256`, `size_bytes`, `source_ref`, `stored_at`.

**`SGN_AUDIT_EVENT`** — журнал, только вставка: `id`, `route_instance_id`, `stage_instance_id`, `event_type`, `payload` (JSON), `actor` (идентификатор реплики), `created_at`. Событие пишется в той же транзакции, что и переход, который оно описывает.

Индексы: по `(status, next_attempt_at)` для выбора кандидатов, уникальные по `external_doc_id` и `request_id`.

## 6. Внешний контракт

Внешней стороны ещё нет: вьюхи и процедуры сделает Oracle-разработчик по нашей спецификации. Задача — описать контракт в `db/contract/` и сделать его заглушку в `db/stub/`. Имя внешней схемы выносится в конфигурацию. Сервис обращается к внешним данным только через эти объекты.

**Вьюха входящих документов**: `doc_id`, `doc_type`, `attributes` (JSON), `content_hash`, `created_at`. Строки не исчезают и не меняются.

**Процедура `create_sign_request(p_request_id, p_doc_id, p_kind, p_signer)`**
- `p_kind`: `AUTO` или `MANUAL`.
- Идемпотентна: повторный вызов с тем же `p_request_id` ничего не создаёт и не падает.
- Не делает `COMMIT` и не использует автономные транзакции.

**Вьюха запросов на подпись**: одна строка на запрос.

| Колонка | Назначение |
|---|---|
| `request_id` | Идентификатор сервиса |
| `status` | `PENDING`, `SIGNED`, `REJECTED`, `ERROR` |
| `status_reason` | Причина отказа или ошибки |
| `signed_at`, `updated_at` | |
| `file_ref` | Относительный путь к подписанному файлу, может быть пустым |
| `file_hash`, `file_size` | Могут быть пустыми |

Гарантии, которые нужно записать в спецификацию:
- Строка появляется сразу после `create_sign_request` в статусе `PENDING` и не исчезает.
- Статус меняется только из `PENDING` в один из конечных, конечный не меняется.
- `SIGNED` выставляется после того, как файл полностью записан и доступен.

**Процедура `cancel_sign_request(p_request_id)`**: идемпотентна, без `COMMIT`. Если запрос уже в конечном статусе, ничего не делает.

Заглушка в `db/stub/` — это таблицы, те же вьюхи и процедуры поверх них. Результат запроса в заглушке выставляется обычным `UPDATE` из теста.

## 7. Движок

### 7.1. Цикл

Каждая реплика в цикле с настраиваемым интервалом выполняет тик:

1. **Обнаружение.** Выбрать из вьюхи входящих документы, которых нет в `SGN_ROUTE_INSTANCE` (анти-джойн). Для каждого найти маршрут по типу, взять старшую версию, вставить экземпляр в статусе `ACTIVE`. Нарушение уникальности (`ORA-00001`) означает, что документ уже вставила другая реплика, это не ошибка. Если маршрута для типа нет, экземпляр создаётся сразу в `FAILED` с причиной `UNKNOWN_DOC_TYPE`.
2. **Выбор кандидатов.** `status = 'ACTIVE'`, `next_attempt_at <= SYSTIMESTAMP`, аренда свободна или истекла. Порядок по `next_attempt_at`, размер пачки из конфигурации.
3. **Обработка.** Для каждого кандидата по очереди: захватить, выполнить один шаг, освободить. Параллелизма внутри реплики нет.

### 7.2. Захват

```sql
UPDATE sgn_route_instance
SET locked_by = :me, locked_until = SYSTIMESTAMP + :lease
WHERE id = :id
  AND status = 'ACTIVE'
  AND (locked_until IS NULL OR locked_until < SYSTIMESTAMP)
```

Одна затронутая строка означает успех, ноль — запись взяла другая реплика, её нужно пропустить.

**Ограждение записи.** Каждая запись состояния после захвата содержит условие `AND locked_by = :me`. Если затронуто ноль строк, аренда потеряна: транзакция откатывается, шаг бросается без побочных эффектов и без увеличения `attempts`.

### 7.3. Шаг

Один шаг — один переход. После шага аренда снимается в той же транзакции.

| Состояние | Действие |
|---|---|
| Текущего этапа нет или он `DONE` | Найти следующий этап маршрута, для которого выполняется условие. Нашли — создать этап в `PENDING`. Не нашли — маршрут `COMPLETED` |
| Этап `PENDING` | В одной транзакции: `IStageHandler.StartAsync` (вызов `create_sign_request`), этап в `REQUESTED`, установить `deadline_at`, сдвинуть `next_attempt_at` на интервал опроса |
| Этап `REQUESTED` | `IStageHandler.CheckAsync` и переход по результату, см. ниже |

Результаты проверки этапа в `REQUESTED`:

- **Подписан.** Если есть `file_ref`: прочитать файл вне транзакции, посчитать SHA-256, сверить с `file_hash` и `file_size`, если они заданы. Затем в одной транзакции сохранить артефакт и перевести этап в `DONE`. Несовпадение хэша или размера — маршрут `FAILED` с причиной `ARTIFACT_MISMATCH`, без ретраев.
- **Отклонён.** Этап `REJECTED`, маршрут `REJECTED`.
- **Ошибка на внешней стороне** (статус `ERROR`). Этап `FAILED`, маршрут `FAILED`.
- **Ещё ждёт, дедлайн не прошёл.** Сдвинуть `next_attempt_at`.
- **Ещё ждёт, дедлайн прошёл.** Вызвать `cancel_sign_request`, этап `EXPIRED`, маршрут `EXPIRED`.

Результат проверяется раньше дедлайна: пришедшая подпись важнее истёкшего срока.

### 7.4. Ошибки

Бизнес-исходы (отказ, таймаут, ошибка внешней стороны) — это штатные переходы. Технические сбои (БД или шара недоступны, файл не найден или занят) обрабатываются отдельно: отдельной транзакцией увеличить `attempts`, сдвинуть `next_attempt_at` с растущей задержкой с верхней границей, снять аренду. После исчерпания попыток маршрут переходит в `FAILED` с причиной `ATTEMPTS_EXHAUSTED`. Успешный шаг обнуляет `attempts`.

Если версии маршрута экземпляра нет в реестре, маршрут переходит в `FAILED` с причиной `ROUTE_NOT_FOUND`.

### 7.5. Абстракции Core

- `IIncomingDocumentSource` — входящие документы.
- `IRouteInstanceStore` — чтение и запись состояния, захват, журнал.
- `ISigningGateway` — создание, проверка и отмена запроса на подпись.
- `ISignedFileSource` — чтение подписанного файла по `file_ref`.
- `IStageHandler` — `StartAsync` (идемпотентный) и `CheckAsync`.

Требование к проектированию: `StartAsync` и перевод этапа в `REQUESTED` должны выполняться в одной транзакции Oracle. Абстракции должны это позволять, например через unit of work, который отдаёт и хранилище, и шлюз на одном соединении. Текущее время движок получает из хранилища, а не из `DateTime.UtcNow`.

## 8. Описание маршрутов

Один класс на тип документа, все версии маршрута в нём, каждый этап — класс:

```csharp
public sealed class ContractRoute : SigningRoute
{
    public override string Code => "contract";

    public override IReadOnlyList<RouteVersion> Versions { get; } =
    [
        new(1, new LegalReviewStage(), new OrgSealStage(), new DirectorStage()),
    ];
}

sealed class DirectorStage : FileSigningStage
{
    public override string Key => "director";
    public override TimeSpan Timeout => TimeSpan.FromDays(5);
    public override Func<DocumentContext, bool>? Condition => doc => doc.GetDecimal("amount") > 10_000;
}
```

Требования:
- Реестр маршрутов по ключу (код, версия). Новые документы получают старшую версию, начатые доходят по своей.
- Проверка при построении: уникальные ключи этапов, положительный таймаут, хотя бы один этап в версии, нет дублей
  версий, не больше одного класса на тип документа.
- Условие этапа вычисляется в момент входа в этап по атрибутам документа.
- Сделать два маршрута-примера: только автоматическое подписание и смешанный с условным этапом.

### Этап 1. Модель и маршруты
- Доменная модель, статусы, `DocumentContext`.
- Классы маршрутов, реестр, проверка маршрутов, два примера.
- **Готово, когда:** тесты покрывают построение, проверку и выбор версии маршрута.

### Этап 2. Движок на фейках
- Абстракции из 7.5, фейковые реализации в памяти с управляемым временем.
- Обнаружение, захват, шаг, обработка ошибок.
- **Готово, когда:** проходят тесты на сценарии:
  1. Маршрут из нескольких этапов проходит до `COMPLETED`.
  2. Этап с невыполненным условием пропускается.
  3. Отказ на этапе завершает маршрут в `REJECTED`.
  4. Таймаут завершает маршрут в `EXPIRED` и вызывает отмену запроса.
  5. Подпись, пришедшая после дедлайна, но до проверки, засчитывается.
  6. Технический сбой даёт ретрай с задержкой, успех обнуляет счётчик.
  7. Исчерпание попыток переводит маршрут в `FAILED`.
  8. Потеря аренды: шаг не оставляет изменений.
  9. Повторный запуск шага `PENDING` не создаёт второй запрос.
  10. Документ, обнаруженный двумя репликами, создаётся один раз.
  11. Неизвестный тип документа создаёт экземпляр в `FAILED`.
  12. Файл недоступен: ретрай. Хэш не совпал: `FAILED` без ретраев.
  13. Каждый переход оставляет запись в журнале.

- `ISignedFileSource` поверх файловой системы: корень из конфигурации, относительный путь из `file_ref`, запрет выхода за корень, таймаут чтения.
- Реализацию через SMB-клиент не делать до решения по вопросу 8.
- **Готово, когда:** тесты покрывают чтение, отсутствие файла, попытку выхода за корень.

### Этап 6. Хост
- `BackgroundService` с циклом тика, options с проверкой при старте, DI.
- Корректная остановка: по сигналу завершить текущий шаг и не брать новые.
- Идентификатор реплики для `locked_by` и журнала: имя пода и случайный суффикс.
- **Готово, когда:** сервис запускается против заглушки и проводит документ по маршруту-примеру.

### Этап 7. Наблюдаемость
- Структурные логи с идентификаторами маршрута, этапа и запроса.
- Метрики: число маршрутов по статусам, возраст самого старого ожидающего этапа, число `FAILED`, время последнего успешного тика.
- Health-эндпоинт. Liveness проверяет только то, что цикл жив, и не зависит от Oracle и шары.
- Перед началом согласовать способ экспорта метрик.

### Этап 8. Контейнер и Kubernetes
- Dockerfile, пример манифестов: Deployment на две реплики, пробы, секреты для Oracle и шары, `terminationGracePeriodSeconds` больше максимальной длительности шага.
- Делать только по отдельному запросу.

## 10. Правила работы

- Не добавляй зависимости сверх названных без согласования.
- Не клади в репозиторий строки подключения и учётные данные, только имена параметров конфигурации.
- Не обращайся к объектам внешней схемы, которых нет в разделе 6.
- Идентификаторы в коде и SQL на английском.
- Если требование противоречиво или не покрыто планом, остановись и спроси.
- В отчёте по этапу перечисляй отступления от плана и их причины.

## 11. Вне объёма

- Пользовательский интерфейс и HTTP API.
- Уведомления подписантам.
- Параллельные этапы, делегирование, возврат на шаг назад, изменение маршрута запущенного документа.
- Эскалации по таймауту.
- Проверка криптографической валидности подписи.
- Очистка данных по истечении срока хранения.
- Ручной перезапуск маршрутов в `FAILED`: пока делается SQL-скриптом вне сервиса.
