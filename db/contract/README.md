# External contract: signing software ↔ signing router service

This document specifies the database objects the signing router service (`Invest.Sign.Router`)
uses in the external schema. They are implemented by the signing software side. The
service accesses the external schema **only** through the objects listed here.

- The external schema name is a service configuration parameter. The service always qualifies
  object names with it, so no synonyms are needed.
- The service and the external schema live in the same Oracle database (19c or newer).
- A reference implementation for development and tests is in [`db/stub/`](../stub).

| Object | Kind | Service needs |
|---|---|---|
| `sign_incoming_document_v` | view | `SELECT` |
| `sign_request_v` | view | `SELECT` |
| `create_sign_request` | procedure | `EXECUTE` |
| `cancel_sign_request` | procedure | `EXECUTE` |

## Transactions

The service calls the procedures **inside its own transaction**, together with writes to its own
tables, and commits or rolls back everything at once. Therefore the procedures:

- **must not** `COMMIT` or `ROLLBACK`;
- **must not** use autonomous transactions (`PRAGMA AUTONOMOUS_TRANSACTION`);
- **must not** execute DDL (it commits implicitly).

If the service transaction rolls back, the effects of the procedure must disappear with it.

## 1. View `sign_incoming_document_v`

Documents to be routed for signing.

| Column | Type | Null | Meaning |
|---|---|---|---|
| `doc_id` | `VARCHAR2(200 CHAR)` | no | Document id, unique within the view |
| `doc_type` | `VARCHAR2(100 CHAR)` | no | Document type; selects the route |
| `attributes` | `CLOB` | yes | JSON object with document attributes used by route conditions |
| `content_hash` | `VARCHAR2(200 CHAR)` | yes | Hash of the source document |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | no | When the document appeared |

Guarantees:

- `doc_id` is unique.
- Rows never disappear and never change once visible.
- A row becomes visible only after the document is complete (committed).
- `attributes`, if present, is a JSON object (`{...}`). Numbers should be JSON numbers; decimal
  strings with a dot separator are also accepted.

The service selects rows absent from its own table (anti-join by `doc_id`), ordered by `created_at`.

## 2. Procedure `create_sign_request`

```sql
PROCEDURE create_sign_request (
    p_request_id IN VARCHAR2,   -- up to 64 chars, generated by the service, globally unique
    p_doc_id     IN VARCHAR2,   -- doc_id from sign_incoming_document_v
    p_kind       IN VARCHAR2,   -- 'AUTO' or 'MANUAL'
    p_signer     IN VARCHAR2    -- signer identifier from the route definition, up to 200 chars
);
```

Creates a signing request. `AUTO` means the signing software signs automatically, `MANUAL` means
an employee signs; the signing software notifies the signer itself.

Guarantees:

- **Idempotent by `p_request_id`.** A repeated call with the same `p_request_id` creates nothing and
  raises no error, even if the other parameters differ. Concurrent calls with the same id must not fail
  either (e.g. catch `DUP_VAL_ON_INDEX`).
- Right after the call, in the same transaction, the request is visible in `sign_request_v`
  with status `PENDING`.
- No `COMMIT`, no autonomous transactions (see above).
- Invalid arguments (unknown `p_kind`, unknown `p_doc_id`) raise an application error
  (`RAISE_APPLICATION_ERROR` in the range -20999..-20000).

## 3. View `sign_request_v`

One row per signing request.

| Column | Type | Null | Meaning |
|---|---|---|---|
| `request_id` | `VARCHAR2(64 CHAR)` | no | Id passed to `create_sign_request`, unique |
| `status` | `VARCHAR2(20 CHAR)` | no | `PENDING`, `SIGNED`, `REJECTED`, `ERROR` |
| `status_reason` | `VARCHAR2(2000 CHAR)` | yes | Rejection or error reason, human-readable |
| `signed_at` | `TIMESTAMP WITH TIME ZONE` | yes | When signed; set for `SIGNED` |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | no | Last status change |
| `file_ref` | `VARCHAR2(1000 CHAR)` | yes | Path to the signed file relative to the share root |
| `file_hash` | `VARCHAR2(64 CHAR)` | yes | SHA-256 of the signed file, hex (case-insensitive) |
| `file_size` | `NUMBER(19)` | yes | Size of the signed file in bytes |

Guarantees:

- The row appears immediately after `create_sign_request` with status `PENDING` and **never disappears**.
- Status changes **only** from `PENDING` to one of the final statuses `SIGNED`, `REJECTED`, `ERROR`.
  A final status never changes.
- `SIGNED` is set **only after** the signed file is completely written to the share and readable.
  From that moment the file at `file_ref` must not change or be removed by the signing software.
- `file_ref`, if set, uses `/` as separator, is relative (no leading `/`, no drive letter) and contains
  no `..` segments.
- `file_hash` and `file_size`, if set, describe exactly the file at `file_ref`. The service verifies
  them and fails the route on mismatch.
- `ERROR` means the signing software cannot complete the request (e.g. invalid certificate).
  The service does not retry it.
- Lookup by `request_id` must be efficient (index or primary key on the underlying table).

## 4. Procedure `cancel_sign_request`

```sql
PROCEDURE cancel_sign_request (
    p_request_id IN VARCHAR2
);
```

Cancels a request when its stage times out.

Guarantees:

- A `PENDING` request becomes `REJECTED` with `status_reason = 'CANCELLED'`; the signing
  software stops waiting for the signer.
- **Idempotent.** For a request in a final status, or an unknown `p_request_id`, does nothing and
  raises no error.
- No `COMMIT`, no autonomous transactions (see above).

## Grants

```sql
GRANT SELECT  ON <external_schema>.sign_incoming_document_v TO <service_schema>;
GRANT SELECT  ON <external_schema>.sign_request_v           TO <service_schema>;
GRANT EXECUTE ON <external_schema>.create_sign_request      TO <service_schema>;
GRANT EXECUTE ON <external_schema>.cancel_sign_request      TO <service_schema>;
```
